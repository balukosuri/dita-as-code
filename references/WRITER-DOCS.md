# Writer documentation

Stage 7 generates these. They are the lasting deliverable: the pipeline runs itself, but the docs
are what let the team understand, trust and teach it.

## Audience floor

Write for a technical writer who **has never used Git**, works in a CCMS UI or Oxygen, and holds no
admin rights. That is the floor, not a caricature - it is the common case in structured-content
teams.

Consequences for every page you generate:

- Every instruction is either something they can do alone, or is labelled with **who** has to do
  it, by role.
- Explain *why*, not just *what*. A writer who understands why the catalog matters will debug it;
  one who copied a command will file a ticket.
- Never assume a terminal. Mention the editor's Git panel as an equal alternative.
- Define a Git term the first time it appears, in a clause, not a glossary.
- Never say "simply", "just" or "obviously".

## What to generate

| File | Purpose |
|---|---|
| `docs/SETUP.md` | One-time per machine. Devcontainer path first, manual path second. |
| `docs/RUNBOOK.md` | The daily loop, plus a troubleshooting section. The page that gets read. |
| `docs/CONTRIBUTING.md` | Three audiences: writers, developers, reviewers. |
| `docs/decisions/*.md` | One ADR per unattended decision. |
| `AGENTS.md` and `CLAUDE.md` | Repository conventions for the team's AI IDE. Identical content. |
| `dac-report.md` | The run report. Generated by `report.py`, not by hand. |

## Placeholders to fill

Fill every one from `detect.json` and `probe.json`. A shipped `{{PLACEHOLDER}}` is a bug.

| Placeholder | Source |
|---|---|
| `{{EDITOR_NAME}}` | the detected authoring tool, by display name |
| `{{DITA_OT_VERSION}}` | the pinned version from `.dac/config.yml` |
| `{{DEFAULT_BRANCH}}` | the repository's default branch |
| `{{CONREF_COUNT}}` | `dita.conref_files`, used to make the reuse argument concrete |
| `{{REPO_LAYOUT}}` | the actual tree, not the template's idealised one |
| `{{CCMS_NAME}}` | the detected CCMS, for the ADR |
| `{{CCMS_ROW}}` | a sync row for the runbook table, or empty |
| `{{CCMS_VERSION_NOTE}}` | the version-drift warning, or empty |
| `{{CCMS_AGENT_NOTE}}` | CCMS-specific agent guidance, or empty |
| `{{HELP_CHANNEL}}` | ask at intake; fall back to "your team's usual channel" |

## Non-negotiable content

These points must survive into the generated docs, because they are the ones that cause silent
damage or wasted days when missing.

**Authoring does not change.** Say it early and plainly. It is the single most reassuring fact
available and the one writers most doubt.

**The ditaval warning.** A build with the wrong filter succeeds and publishes wrong content. Frame
it as the failure mode to take most seriously, because it is invisible.

**Never rename a DITA file with `mv`.** Use the editor's refactoring command. This will otherwise
happen in the first week.

**A green build is not proof references resolved.** Explain why the separate reference check
exists, so nobody "simplifies" it away later.

**Vale does not cover `.ditamap`.** State the gap rather than implying full coverage.

**Version alignment across three places** - machine, CI, editor - and for CCMS teams, the CCMS
toolkit as a fourth. Name the real numbers: Heretto caps at 3.7.4, IXIA defaults to 2.5.4, AEM
ships 3.3.2, against 4.4.1 current.

**Why the XML formatter earns its place.** Readable diffs are what make DITA review work. Without
that explanation it looks like gratuitous tooling and someone removes it.

## Honesty requirements

Overclaiming is the fastest way to lose a non-expert audience, because they will discover the gap
at the worst possible moment.

- **Do not promise a VS Code DITA authoring experience.** It does not exist. Red Hat XML gives
  validation and navigation; DitaCraft is a small single-maintainer project. Writers stay in their
  editor.
- **Archetype C is not fully docs-as-code.** Flare and unstructured FrameMaker teams get Git, CI,
  linting and publishing. They do not get semantic diffs or component reuse. Say both halves.
- **Do not say "DITA 2.0".** It is not an OASIS standard; the newest formal document is a 2018
  public review draft, and DITA 1.3 remains current. LwDITA 1.0 is likewise unratified.
- **Name what each degrade path costs**, not only what was installed.
- **CCMS review stays in the CCMS.** Do not imply pull requests replace subject-matter review for
  archetype B.

## ADRs

Write one for every decision made without asking. Each needs: context, the decision, alternatives
with the real reason each was rejected, and **how to switch later**.

The closing note matters as much as the decision. A writer reading an ADR six months from now needs
to know the choice was deliberate and reversible, not accidental.

Expected ADRs:

- CCMS as system of record with one-way sync (archetype B) - template provided
- Repository granularity for reuse: one repository per product family by default
- Pinned DITA-OT version and why it matches the editor's bundled version
- Container versus native build path, where Java was unavailable
- Adopting existing CI rather than replacing it, where CI already existed
